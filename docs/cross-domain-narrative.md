# 跨領域背景敘事技巧

> 非本科、轉職或跨產業經驗不需要被包裝成「從零開始」。好的敘事會讓雇主看懂：你做過哪些工作、哪些能力能轉用、證據在哪裡，以及你正如何補足差距。

---

## 一、先改寫問題：不是「我從哪裡來」，而是「我能證明什麼」

跨領域求職最常見的失誤，是只說自己「很有熱忱、學得很快」，或把過去職稱直接換成目標職稱。前者太抽象，後者則可能失真。比較有說服力的做法，是從目標職缺的實際任務出發，找出自己已做過的相近工作與可驗證成果。

!!! tip "一句話定位公式"
    **既有背景＋可驗證經驗＋目標方向＋可帶來的價值**。例如：「具備零售營運與資料分析經驗，曾整理跨部門流程與追蹤指標，現聚焦產品營運職務，能協助團隊把使用者回饋轉為可執行的改善項目。」

職稱、科系、能力與工作任務並不是同一件事。以資安領域為例，NIST 的 NICE Framework 以工作任務、知識與可觀察技能描述人力需求，並提醒 Work Role 不等同於職稱或職業。因此，先對照任務，比急著替自己貼上新標籤更可靠。[NIST NICE Framework](https://www.nist.gov/itl/applied-cybersecurity/nice/nice-framework-resource-center/getting-started)

把目標職缺拆成下列四欄；先求誠實完整，再挑出最有力的兩到三條放進履歷與面試。

| 目標職缺要完成的任務 | 已有可轉移能力 | 可提出的證據 | 還要補強什麼 |
|---|---|---|---|
| 與不同角色釐清需求 | 訪談、協作、文件整理 | 會議產出、流程改善、交付物 | 目標產業術語與情境 |
| 分析問題並提出做法 | 資料判讀、除錯、研究 | 決策紀錄、專案成果、作品集 | 專業方法或工具 |
| 推動方案落地 | 排程、溝通、風險管理 | 里程碑、回饋、改善結果 | 目標職務的責任範圍 |

---

## 二、找出可轉移能力：從任務對照，不從形容詞對照

「溝通力佳」或「抗壓性高」很難讓人判斷程度。改用動詞和情境：你和誰合作、處理什麼限制、做了哪些判斷、造成什麼結果。履歷的相關性也不只來自職稱；非直接相關的工作，仍可用來證明目標職缺需要的能力。[Berkeley Career Engagement：Resumes](https://www.career.berkeley.edu/prepare-for-success/resumes/)

常見的轉換路徑包括：

- **專業轉換**：把既有技術、分析或設計能力，連到新職務的任務與產出。
- **產業轉換**：把對原產業使用者、流程、法規或供應鏈的理解，轉成新職務可用的情境判斷。
- **職能轉換**：把客服、教學、營運或專案協作經驗，連到需求釐清、利害關係人溝通與推動落地。

跨領域背景本身不是優勢；能以事實連到職缺任務，才可能形成差異化。若沒有直接經驗，清楚說明「目前能做什麼」與「正在補什麼」，通常比聲稱已有完整能力更有可信度。

---

## 三、選擇證據：成果優先，自學清單放後面

雇主需要的是能被追問、能說明自己角色的證據。實務技能、工作經驗與工作影響是判斷能力的重要材料；課程與證照能傳達投入程度，但不能取代成果本身。[NIST：Identifying Proficiency](https://www.nist.gov/itl/applied-cybersecurity/nice/nice-framework-resource-center/identifying-proficiency-nice-framework)

可依下列順序盤點素材：正式工作或實際交付、可展示且已去識別的專案、跨角色協作與決策成果、練習作品或課程作業、證照與課程。這不是通用的官方排名，而是幫助你優先呈現最能被驗證內容的方法。

履歷條列可套用這個句型：

> 在＿＿情境中，運用＿＿方法處理＿＿問題；與＿＿協作，在＿＿限制下完成＿＿，使＿＿得到改善。

例如，不要只寫「協助優化流程」，可改為「整理客服回報並與工程、營運共同定義分類規則，將重複問題轉為每週追蹤清單，協助團隊聚焦優先改善項目。」沒有可靠數字時，不必硬湊百分比；描述範圍、頻率、交付物與可查核變化，同樣能讓貢獻具體。更多寫法可參考[履歷寫作](resume-writing.md)。

!!! warning "不要把學習經驗寫成正式經驗"
    Lab、課程、社群練習或協助工作都可以寫，但要標示真實情境與參與程度。可用「接觸過 → 協助 → 在指導下執行 → 獨立執行 → 主導 → 在正式環境負責」檢查措辭是否超過事實。

## 四、讓履歷、平台與面試說同一條事實主線

不同媒介的篇幅不同，核心事實卻必須一致。日期、職稱、參與範圍與成果若彼此矛盾，面試官很容易失去信任。

| 媒介 | 主要回答的問題 | 適合的呈現方式 |
|---|---|---|
| 履歷 | 你有哪些相關證據？ | 精簡成果條列、關鍵技能、可驗證產出 |
| 求職平台 | 為何轉向、能帶來什麼？ | 一段背景脈絡加目標職務價值 |
| 面試 | 你如何判斷、行動與反思？ | 一到兩則具體案例，說清自己的角色 |
| 作品集 | 你能否實際完成？ | 可檢查的產出、限制、取捨與下一步 |

面試時可用 STAR(R) 結構：情境（Situation）、任務（Task）、行動（Action）、結果（Result），最後補上反思（Reflection）。重點不只在結果，也在你如何思考、做了哪些假設、如何和他人協作；這正是 Microsoft 建議求職者具體呈現思考過程的原因。[Microsoft Careers：Interview tips](https://careers.microsoft.com/v2/global/en/hiring-tips/interview-tips.html) 想練習案例拆解，可接著看[面試準備](interview-prep.md)。

## 五、示範：從全端工程走向應用程式安全或資安顧問

以下是方法示範，不代表所有人都具備相同經驗，也不表示開發背景可直接等同資安年資。

一位有全端開發經驗的求職者，可能把經驗映射為：理解程式碼、API 與部署流程；曾和產品、工程人員釐清需求；能把風險或缺陷轉成可執行的修正項目。這些都能連到應用程式安全工作中的安全設計、程式碼與 CI/CD 流程、工具導入或風險溝通。安全實務也可整合進既有的軟體開發生命週期；NIST SSDF 將此描述為可依風險與環境調整的結果導向做法。[NIST SP 800-218](https://csrc.nist.gov/pubs/sp/800/218/final)

但敘事仍要保留缺口，例如：尚未主導滲透測試、未在正式環境負責資安治理，或正在累積威脅建模與安全驗證經驗。OWASP ASVS 可作為 Web 應用程式安全需求與測試基準的參考，卻不能單獨證明已具備完整應用程式安全或顧問能力。[OWASP ASVS](https://owasp.org/www-project-application-security-verification-standard/)

資安顧問也不只有技術交付；溝通、批判思考、影響利害關係人與持續學習同樣重要。[NIST：Workplace Skills](https://www.nist.gov/itl/applied-cybersecurity/nice/nice-framework-resource-center/resources/workplace-skills-and-nice) 因此，這類背景可以準備三種故事：如何降低一項技術風險、如何將複雜問題說給非技術角色聽、以及如何在限制下推動改善。每一則都要區分自己做了什麼與團隊做了什麼。

!!! note "示範的目的，是建立映射，不是複製職稱"
    有些資安職缺接受軟體工程或資訊背景，有些則要求特定資安、風險或產業經驗。閱讀職缺時應以當下的任務與門檻為準，不要把單一公司或地區的條件外推成普遍規則。

## 六、送出前檢查

- [ ] 我能用一句話說出目標職缺、既有證據與想帶來的價值。
- [ ] 每一項關鍵能力都有真實案例、作品或交付物可以追問。
- [ ] 我已分清楚個人貢獻、團隊成果與正式／練習情境。
- [ ] 履歷、求職平台與面試中的日期、職稱、成果相互一致。
- [ ] 我沒有把課程、Lab 或協助經驗寫成獨立負責的正式工作。
- [ ] 所有數字都有期間、比較基準與可說明的來源；沒有數字時也寫清楚範圍與產出。
- [ ] 我能坦白說明一到兩項能力缺口，以及正在採取的補強行動。

---

## 七、本頁重點回顧

跨領域敘事的目標不是掩蓋過去，而是建立一條能被驗證的連線：**目標任務 → 可轉移能力 → 真實證據 → 補強計畫**。當履歷、平台與面試都沿用這條主線，背景差異就不再只是風險，而能成為你看待問題與合作方式的具體證明。
