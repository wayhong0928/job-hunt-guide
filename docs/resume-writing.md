# 履歷寫作

> 這一頁談的是內容，不是排版美學。一份履歷能不能過招募者的第一輪掃視，關鍵在於每一條經歷是不是寫成了「成果」而不是「職責清單」。

---

## 一、先回答「為什麼你適合這個職缺」

柏克萊與哈佛的職涯中心都指出，履歷應該依職缺調整，而不是把人生經歷完整列出來。常見的核心區塊是聯絡資訊、專業摘要（選用）、相關經驗與成果、教育、技能，再依職缺加入專案、證照或作品集；工作與學歷通常採倒序排列。

排序原則要依你的資歷狀態調整：

- 學生或相關工作經驗較少者：把教育、實習與專案往前放。
- 已有相關全職經驗者：把工作成果往前放，教育往後移。

**建議的區塊順序（依情況調整）**：

1. 姓名與聯絡方式（Email、電話、所在地、LinkedIn／作品集連結）
2. 專業摘要：兩到四行，說明定位、核心經驗與能帶來的價值；如果經歷很少、摘要只會重複正文內容，可以省略這一段
3. 相關經驗：以成果條列為主，不是複製職務說明
4. 專案：凸顯與目標職缺直接相關的技術、角色與結果
5. 技能／證照：只列能在面試中舉證的內容，依職缺優先順序排列
6. 教育：學位、學校、期間；課程或論文只保留相關項目

!!! tip "投遞前的自我檢查"
    建一張三欄表：**職缺要求 → 履歷中哪一條證明 → 尚缺什麼證據**。柏克萊職涯中心要求每項成果都對應雇主所需能力，密西根大學則建議直接從職缺關鍵字準備證明故事，這張表就是把兩個建議合在一起的做法。

## 二、量化成就：數字要能解釋，不是為了量化而量化

### 2.1 可以直接套用的句型

耶魯大學職涯中心提出的 APR 架構，把每一條成果拆成三段：Action（行動）＋ Project/Problem（專案或問題）＋ Result（結果）。也可以用另一種寫法：「完成 X，以 Y 衡量，透過 Z 做到」。

```text
[強動詞] + [做了什麼] + [如何／在何種限制下] + [產生何種結果]
```

```text
透過 Z，完成 X，結果由 A 改善至 B／影響 Y。
```

量化不是只能用百分比，金額、時間、件數、使用者數、服務範圍、品質、錯誤率、交期或前後對照都算數字。以下是幾組弱版與強版的對照，都是通用示範素材：

- 弱：「負責每月營運報表。」
  強：「重整月結報表自動化流程，使完成時間由三天縮短至一天，每月節省約十六工時。」
- 弱：「協助 API 開發。」
  強：「設計並實作六支訂單 API 的權限檢查與錯誤處理，補齊高風險操作的授權測試，並在發布前完成複測。」
- 弱：「參與弱點掃描。」
  強：「整理掃描結果並人工複核高風險項目，將可重現問題轉為開發驗收條件，協助團隊於版本發布前完成修正與複測。」

### 2.2 沒有可信數字時，不要硬湊

哈佛與耶魯都鼓勵量化，但沒有要求每一條都掛數字。沒有基準、無法在面試中說明清楚的數字，反而會變成可信度風險。面試官只要追問一句「這個百分比是怎麼算出來的」，答不上來就會留下不好的印象。

!!! warning "數字自我檢查"
    每個數字都要能回答四件事：資料從哪裡來、比較基準是什麼、本人貢獻占多少、計算期間多長。答不出來，就改用可驗證的範圍描述，寫清楚規模、角色與交付物，也是一種可信的呈現方式。

## 三、動詞選擇：具體表達影響類型

強動詞應該放在條列開頭，而且後面要接對象、方法與結果。「負責」「協助」這類詞本身不能說明成果，補上動詞不會讓句子自動變強。

| 目的 | 中文動詞 | 英文動詞 |
|---|---|---|
| 成就／改善 | 達成、提升、降低、縮短、優化、重整 | Achieved, Improved, Reduced, Streamlined, Transformed |
| 領導／管理 | 帶領、統籌、協調、培育、監督 | Led, Directed, Coordinated, Mentored, Supervised |
| 建置／技術 | 設計、開發、部署、自動化、測試 | Designed, Developed, Deployed, Automated, Tested |
| 分析／研究 | 分析、評估、驗證、調查、建模 | Analyzed, Evaluated, Validated, Researched, Modeled |
| 溝通／影響 | 提案、簡報、協商、撰寫、促成 | Proposed, Presented, Negotiated, Authored, Influenced |
| 教學／支援 | 指導、培訓、促進、解決、諮詢 | Coached, Trained, Facilitated, Resolved, Advised |

英文時態應該反映經歷狀態：現職持續性工作通常用現在式，已完成的成果與過去職務用過去式，同一類條列內保持時態一致就好，不需要把所有現職內容都硬改成過去式。

## 四、常見地雷：五個容易被忽略的類別

哈佛職涯中心把履歷常見問題分成內容、證據、相關性、版面與誠信五類，104 與 ATS 相關指南也各自補充了在地與技術面的地雷：

- 錯字、Email 或電話錯誤、日期前後不一致
- 只抄職責，沒有說明本人行動與結果
- 未依職缺客製，技能清單與應徵方向失焦
- 版面過度美編、字太小、資訊密度過高導致難以掃讀
- 職稱、年資、技術熟練度或成果數字誇大
- 把團隊成果全部寫成個人成果
- 披露客戶名稱、弱點細節、內部架構或前公司機密
- 履歷、LinkedIn、104、Cake 各平台之間的日期、職稱或成果互相矛盾

有業界統計指出，招募方對含有明顯 AI 生成痕跡的履歷會有疑慮，部分甚至視為關鍵扣分項。用 AI 工具協助草擬或改寫履歷文字之後，最後一定要自己再過一輪，把罐頭式的排比句、空泛的形容詞修掉，讓文字讀起來像自己會講的話。

!!! note "地區差異，不是通用規則"
    國際化英文履歷通常避免放照片、年齡、性別、婚姻等非必要個資；104、Cake 等台灣平台則可能提供照片欄位。這是市場與平台慣例的差異，不能把任一種做法當成全球通則，投遞前留意目標市場的慣例即可。

## 五、履歷長度：一頁是常見起點，不是鐵律

一頁是學生、新鮮人與經歷較少者的常見起點，但不是所有人的硬規則。如果刪除不相關內容後仍有大量直接相關成果，兩頁也可以接受；資深、技術、研究、政府、醫療或學術取向的履歷可能更長。核心判準是可讀性與相關性優先於頁數本身，不要為了填滿兩頁而灌水，也不要為了硬塞一頁而犧牲重要內容。

一個實用的自我提問是：如果我把這份履歷刪到剩一頁，會不會漏掉任何一條招募者非看不可的成果？如果答案是不會，那就維持一頁；如果會，再考慮延伸到第二頁。

## 六、ATS：求職者追蹤系統怎麼過關

多數企業會先用 Applicant Tracking System（求職者追蹤系統，簡稱 ATS）過濾履歷，再交給真人閱讀。ATS 友善的版面應該是標準、線性、可抽取文字的格式：

- 用單欄，避免文字方塊、表格、多欄設計。多數 ATS 是由左至右、由上至下單向讀取，雙欄版面容易讓解析器把內容順序讀亂
- 用標準字型（Arial、Calibri、Times New Roman、Garamond 等），大小 10 到 12pt
- 圖表、照片、技能等級長條圖等視覺元素能免則免，對人眼美觀，但對解析器可能造成資料錯亂
- 章節標題用業界標準用語，像 Work Experience、Education、Skills，方便系統正確分類
- 聯絡資訊放在正文，不要依賴頁首或頁尾

關鍵字應該從目標職缺說明裡擷取，只放入真實經驗脈絡，不要堆疊或隱藏字詞。優先辨識職稱、硬技能、工具、證照、學歷與反覆出現的產業術語；縮寫第一次出現時建議寫全名加縮寫，例如「資安事件管理系統（Security Information and Event Management, SIEM）」。如果職缺寫的是「stakeholder communication」，履歷卻寫「working with leadership」，部分系統無法連結兩者語意，比對分數就會下降，盡量貼近職缺原文的用字。

檔案格式以職缺頁面的指示為最高優先。DOCX 通常被視為較保守的 ATS 選擇，現代系統也可能接受文字型 PDF，但影像掃描、複雜圖層或特殊排版仍可能解析失敗，不能一概而論說「PDF 一定不過」或「PDF 永遠最安全」。

!!! warning "沒有通用的合格公式"
    目前查無跨所有 ATS 通用的關鍵字密度、合格分數、排名公式或「照做必過」門檻。各企業使用的系統與設定不同，上述做法只能提高可解析性與職缺相關性，不能保證取得面試機會。如果你的履歷本身排版含多欄或圖形化設計，投遞時可以另存一份純文字單欄的 ATS 安全版，展示用的視覺化版本則留給 LinkedIn 或 Cake 之類的平台。

## 七、本頁重點回顧

- 履歷要依職缺調整，先建「職缺要求 → 履歷證據 → 尚缺什麼」三欄表，比反覆修飾形容詞更有效。
- 每條成果盡量套 APR 句型：行動＋專案或問題＋結果；沒有可信數字時改用可驗證的範圍描述，不要硬湊百分比。
- 強動詞開頭，後面接對象、方法與結果；「負責」「協助」本身不能說明成果。
- 常見地雷分五類：內容空泛、缺乏證據、與職缺不相關、版面難讀、誠信瑕疵（含跨平台資訊矛盾）。
- 一頁是常見起點而非鐵律，可讀性與相關性優先於頁數。
- ATS 友善版面用單欄、標準字型、標準欄名；關鍵字取自職缺原文，但沒有任何通用公式能保證過關。
- AI 協助草擬後務必自己再潤飾一輪，避免罐頭式措辭讓招募者一眼看穿。
