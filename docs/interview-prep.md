# 面試準備

> 面試準備的核心不是背答案，是把「我做過什麼」轉成「我能證明什麼」。這一頁涵蓋 STAR 法、行為面試、技術面試、談薪與反問問題。

---

## 一、先建立「能力、題型、證據」矩陣

在準備任何具體問題之前，先拆解目標職缺公告裡寫的技能、情境與成果責任，再為每一項能力準備一則可驗證的故事。密西根大學職涯中心建議標記職缺關鍵字並準備對應的證明故事，微軟的面試指南也會評估求職者的履歷、職能與技能如何轉用到新職務上。

建議整理成一張表，投遞前跟每場面試前都拿出來複習：

```text
職缺責任 → 要證明的能力 → 可能題型 → STAR 故事 → 可查證指標 → 尚缺證據
```

這張表最大的用處，是逼你發現「尚缺證據」那一格。與其臨場編一個聽起來合理的答案，不如提早發現缺口，用接下來的準備時間補上，例如做一個小專案，或爭取一次相關的任務。

---

## 二、STAR 法：背景要短，行動與結果要長

STAR 是 Situation（情境）、Task（任務）、Action（行動）、Result（結果）四段式的回答架構，被多所大學職涯中心與企業面試指南一致採用。

| 段落 | 回答內容 | 自我檢查 |
|---|---|---|
| Situation | 系統、客戶或專案出了什麼問題 | 是否只留下理解故事所需的背景，沒有多餘細節？ |
| Task | 本人負責的範圍、目標與限制 | 是否區分清楚團隊任務與個人責任？ |
| Action | 診斷、取捨、協作、實作與驗證 | 是否說出判斷依據，而不是只說「我們做了」？ |
| Result | 技術成果、風險或營運影響、回饋 | 是否可驗證？如果失敗了，是否說明後續修正？ |

一個常被忽略的延伸是 Reflection（反思）：學到什麼、下次會怎麼做不同。微軟等企業採用的 STAR(R) 架構就把反思納入正式的一環。Action 通常是整段回答篇幅最長的部分，建議用「我」而不是模糊的「我們」來描述決策與判斷過程；Situation 與 Task 保持簡短，把時間留給 Action 與 Result。整題控制在六十到九十秒、口說約一百五十到兩百字是常見的節奏參考，不是硬性規定。

!!! tip "空泛的 STAR 已經不夠用"
    有觀察指出，只套用 STAR 架構、但結果段落沒有具體數字的回答，愈來愈難讓面試官滿意。Result 段落一定要有可衡量的佐證，這跟履歷寫作要求量化的紀律是一致的，見[履歷寫作](resume-writing.md)第二節。

## 三、行為面試題型與故事庫

準備六到八則可以重複轉用的故事，覆蓋以下八類能力，是被反覆提到的建議。微軟明列協作、成果導向、顧客導向、影響力、判斷力、適應力等面向，NIST 的 NICE 職場技能框架也把溝通、衝突管理、批判思考、彈性、影響力與主動性列為資安職場必備技能，可以互相對照：

1. **協作**：跨前端、後端、DevOps、產品或客戶建立共識
2. **衝突／影響**：不同角色對時程、風險或優先級意見不一
3. **成果導向**：在限制下改善品質、速度、覆蓋率或風險
4. **顧客／利害關係人**：釐清真正需求並處理期待落差
5. **判斷與取捨**：資訊不足時如何排序與升級處理
6. **適應與學習**：快速理解陌生技術、產業或框架並落地
7. **失敗與反思**：承認錯誤、修正並改變流程
8. **主動性**：找出沒人明確指派、但值得解決的問題

每則故事至少準備一項核心能力、一項技術或專業判斷、一項可驗證結果、一項反思，這樣同一則故事就能依面試官的追問方向靈活切換重點。典型題幹是「Tell me about a time when」「Give an example of a time when」這類開頭，準備時可以先把自己的故事庫按上述八類分類好，面試現場再依題目挑選最貼近的一則。

## 四、技術面試：依職能分開準備

### 4.1 軟體工程師

準備層次建議涵蓋：需求澄清、拆解與設計、可執行程式碼、測試與邊界條件、安全影響，再依職缺補強演算法、資料結構、分散式系統與網路基礎。微軟的技術面試指南明確要求求職者先口頭澄清功能與非功能需求，提出計畫後再用熟悉的語言寫出可執行的程式碼，並主動測試錯誤情況。

準備清單：

- [ ] 能以口頭方式澄清功能與非功能需求
- [ ] 能解釋資料結構、演算法與時間／空間取捨
- [ ] 能討論系統設計：介面、資料流、失敗模式、擴充性與觀測性
- [ ] 能實際寫碼並自行測試正常、邊界與錯誤案例
- [ ] 熟悉 Web／API 安全基礎：驗證、授權、輸入處理、敏感資料、日誌與依賴管理
- [ ] 能從自己履歷中的專案往下追問架構、失敗經驗與本人貢獻

近年的趨勢是及格標準提高，AI／LLM 相關基礎設施題目（例如設計推薦系統、RAG pipeline、模型服務層）已經進入一般工程面試流程，中階工程師也被期待要能設計可擴展的系統並論證架構取捨。多數公司目前也明確允許或討論在面試中使用 AI 輔助工具的界線，投遞前可以先確認該公司的立場。

### 4.2 資安顧問

資安顧問面試不只考工具操作，也考如何把現況轉成風險評估、優先順序、改善路線圖，以及能讓客戶採行的具體建議。企業案例中，應用程式安全相關職缺常涵蓋差距分析、威脅建模、設計審查、程式碼／API／基礎設施即程式碼／CI/CD 的檢視，以及向管理層呈現結果；顧問類職缺則要求把資安問題轉譯成商業風險，同時兼顧控制措施、工作坊帶領與簡報能力。

案例練習可以套用這個框架：

```text
新 API／雲端服務上線
→ 釐清資產、資料、使用者與威脅
→ 找出控制缺口
→ 依可能性、衝擊、成本與可行性排序
→ 提出近期與中期改善路線圖
→ 定義責任人、期限與驗證方式
```

軟實力同等重要：要能用商業語言解釋複雜的技術概念，因為顧問角色需要同時與技術人員和高階主管溝通。建議準備五到七個涵蓋不同面向的故事，包括危機處理、利害關係人溝通、技術問題解決、商業對齊。技術背景怎麼幫助自己做顧問溝通，本身就是很值得準備的一則故事。

### 4.3 MIS／資管背景

如果職缺強調企業 IT 而非純軟體開發，準備方向不應該只做演算法題。系統分析師的典型工作包括與管理者確認 IT 角色、成本效益、系統設計與測試、使用者訓練；資安分析師則涵蓋監控、弱點管理、報告撰寫、標準遵循、向管理層建議與災難復原規劃。

目前業界資料多半以職能（軟體工程師、資安顧問）而不是學術科系來分類面試準備指南，並沒有找到專屬 MIS 或資管系背景的獨立面試準備資料。這是合理的現象，因為面試官通常看職能而非科系。實務上的建議是：MIS 或資管背景直接套用軟體工程師與資安顧問兩組準備重點，科系背景本身則放進履歷或自我介紹裡，當成「為什麼同時懂技術又懂商業流程」的敘事素材（詳見[跨領域背景敘事技巧](cross-domain-narrative.md)）。

## 五、薪資談判

正式的薪資談判通常在取得 offer 之後、接受之前進行。先研究相同地區、職務與經驗層級的市場行情，決定自己的底線，再評估總報酬。獎金、股票、彈性工時都算在內，不要只鎖定底薪數字。部分新人培訓職或統一職級的職位，議價空間可能天生有限，這點要提早認知。

常見話術（依情境調整用字）：

- 面試前期被問期望薪資：「我很樂意討論待遇，可以先分享一下貴公司這個職位核定的薪資區間嗎？」
- 必須先報區間時：「依目前了解的職責、地點與相近職務的市場資料，我期待底薪大約在 X 到 Y 之間；如果實際範圍或整體報酬不同，我也願意一起討論。」
- 收到 offer：「謝謝，我對這個職務很有興趣。可以先提供完整的書面方案，讓我在某個日期前評估嗎？」
- 提出還價：「考量這個職務需要同時涵蓋⟨技術能力⟩與⟨商業溝通能力⟩，以及我能帶來的⟨具體成果⟩，想請問底薪是否有調整到 X 的空間？」
- 底薪確實受限時：「如果底薪級距固定，是否能討論調薪檢視時間、證照與訓練預算、遠距安排、休假或簽約金？」

台灣在地的做法上，104 等平台的實務文章建議先做功課了解市場平均薪資、前一份工作薪資水準與該公司開出的職缺待遇範圍，據此界定喊價區間；迴避直接報數字時可以說「期望待遇不低於某個數字」或「跟我資歷相近的人大概能拿多少」。避免說「依公司規定」，這等於把議價權完全交給對方；也不要謊報前公司薪水，因為許多公司核薪會要求提供薪資證明，說謊容易被拆穿。薪資談判最好留到面試尾聲，等對方已經清楚你能帶來的價值後再談。

!!! warning "誠信界線"
    不要虛構競爭 offer、目前薪資、職級或市場資料。任何要填入的具體金額，都需要依應徵地、公司、職級與當下的市場行情另行查證，本頁的話術範本只是句型參考，不代表任何具體數字。

## 六、反問面試官：用提問驗證這份工作

面試尾聲的反問環節，是候選人評估這份工作是否適合自己的機會，不是走過場的形式。建議準備五到七題，依面試官角色挑選三到五題發問；同一天遇到不同面試官，問題也應該依對方的角色調整。

一般共通問題：

- 「這個職位在到職後三十、六十、九十天內最重要的任務是什麼？」
- 「我的表現會怎麼被評估？」
- 「團隊通常是協作還是各自獨立作業？」
- 「您的管理風格偏向給明確指示任務，還是期待我主動提出方向？」

顧問或客戶導向職缺可以問得更聚焦（以資安顧問為通用示範，可依自己的職缺調整）：

- 「一份弱點或差距報告，通常如何轉成實際的修復路線圖？顧問是否會參與修復驗證？」
- 「開發、維運、稽核與業務對風險優先順序意見不同時，通常怎麼決策？」
- 「對從軟體工程轉入顧問角色的人，最常見的能力缺口是什麼？有沒有相關的訓練或帶領機制？」
- 「技術實作、報告簡報、提案與客戶會議大約怎麼分配時間？」

避免問官網或招募資料就查得到的問題，也避免太空泛的「文化如何」，這類問題招募者往往只會給罐頭答案。好的問題聚焦在面試官個人與具體事件，例如「有沒有一次公司文化真正影響到專案走向的經驗？」對方回答之後，順著細節追問下去比急著換到下一題更容易讓對話深入；如果面試官回答簡短或明顯在看時間，也要懂得優雅收尾。對顧問或客戶導向職缺來說，這種懂得追問、營造對話感的能力，本身就是在向面試官示範你未來與客戶互動的方式。

## 七、本頁重點回顧

- 先建「能力、題型、證據」矩陣，把職缺要求拆解成一則則可驗證的故事，提早發現證據缺口。
- STAR 架構裡 Action 與 Result 篇幅最長；Result 一定要有可衡量的佐證，加上 Reflection 更完整。
- 準備六到八則故事覆蓋協作、衝突、成果導向、顧客溝通、判斷取捨、適應學習、失敗反思、主動性八類能力。
- 技術面試依職能分開準備：軟體工程看拆解設計與程式碼，資安顧問看風險轉譯與客戶溝通，MIS 背景可以套用兩者並把科系背景放進敘事素材。
- 薪資談判先做功課、報範圍不報單一數字、留到面試尾聲；不虛構任何數字或競爭 offer。
- 反問問題聚焦具體事件而非空泛文化，回答後順著細節追問，是顧問職缺的加分技巧。
